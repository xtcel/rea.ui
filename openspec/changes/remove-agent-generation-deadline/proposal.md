## Why

改一次较大的界面时，生成本来就慢：Codex 要先读设计文件和参考、写完多个页面再自检。现有实现给它设了 10 分钟的墙钟上限，到点直接 kill 子进程并报「生成超过 10 分钟，已停止。可以缩小需求后重试。」——用户的需求没有错，慢是正常现象，却被迫拆成小段重来，而且重来一次还要重新读上下文，往往更慢。API 提供商的流式读取同样在 600 秒处截断，问题一致。

真正的失败信号是「进程退出」和「长时间完全没有新数据」，不是「已经跑了多久」。所以按总时长判定失败不合理，应当去掉。

## What Changes

- 删除 Codex 任务的 600 秒墙钟上限：不再因为运行时间长而 `kill` 子进程，也不再写入「缩小需求后重试」。
- 删除 API 流式读取的 600 秒总时长上限。
- 连续一分钟没有新进度时，把最后一条进度更新为「仍在生成 · 已用时 N 分钟」（只保留一条，不刷屏），让用户能区分「还在跑」与「卡死」。
- 流式读取报错时给出「连接中断（原因）」而不是静默 break 后落到「没有返回内容，请检查模型名称与额度」。
- 客户端每次读取的空闲超时（660 秒）保持不变，它约束的是「连接是否还活着」，不是任务总时长。

## 范围说明

- 不改用户停止（`cancel`）的语义：停止仍然立即标记 `cancelled` 并终止子进程。
- 不改 `MAX_RESULT` / `MAX_PROMPT` / `MAX_RESPONSE` 等大小限制。
- 不改 Gemini 的一次性 `generateContent` 调用方式（仍未改流式），其连接超时沿用现有客户端设置。
- 不在前端新增计时器或自动重试。

## Impact

`crates/local-agent/src/lib.rs`、`crates/local-agent/src/provider.rs`、`docs/local-agent.md`、`docs/settings.md`、本变更新增的 `editor-agent-workspace` 契约增量、`docs/verification.md`。前端与文档格式不受影响。
