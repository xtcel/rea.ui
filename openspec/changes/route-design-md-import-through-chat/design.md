## Context

`DesignSystemPage` 有两个接收文件的入口：

1. 顶栏「导入 DESIGN.md」、创建引导卡「导入 DESIGN.md / CSS」、更多菜单「导入 DESIGN.md / CSS」——三者共享 `importInput` 与 `handleImport`。
2. 对话输入框左侧「＋ 附加参考文件」——只把文件放进 `attachments`，用户自己写需求再发送。

`handleImport` 原先按扩展名分流：`.md/.markdown` 走 `importDesignMarkdown()` 同步解析并直接替换草稿；其它扩展名才 `send()` 交给 Agent。于是散文型 DESIGN.md 在入口处被当成非法契约拒绝，而它恰恰是 Agent 最擅长处理的输入。

## Decisions

### D1：入口只做暂存与预填，发送由用户确认

探测 frontmatter 再二选一，会把「这份文件属于哪一类」的知识负担留给用户：契约文件静默替换草稿，散文文件进入对话，两种结果都不可预期。但直接自动发送也有代价：用户来不及补充上下文，选错文件就已消耗一次生成，想改提取范围也只能等结果出来再追加一轮。所以入口只把文件挂到附件、把指令预填进输入框，光标落到末尾；发送仍走同一条 `send()` 路径，由用户按下 Enter 或发送按钮完成。

### D2：解析能力留在库层，撤出的只是 UI 的自动解析

`importDesignMarkdown()` 仍服务 CLI（`reaui validate --system` 之外的转换脚本）、测试和未来的精确导入入口。删除它会把「往返稳定」这条已验证的契约降级成无入口代码；本变更只让 `DesignSystemPage` 不再调用它。

### D3：契约保真靠提示词，而不是解析器

发送后统一由 Agent 提取，预填指令要求「优先沿用文件里的颜色、排版、圆角与组件规范」。这是有损的兜底：模型可能改写小数或漏掉 `states`。接受该取舍，因为在设计系统页的主要场景里，用户拿的是外部风格文档，而不是自家导出的包；自家包的往返由库函数与 CLI 保证。

### D4：正在生成时不接收新文件

生成期间输入框与附件按钮都是禁用态，此时挂文件只会让用户在解除禁用后才发现内容没生效。`handleImport` 先给出明确错误，避免文件凭空消失。

### D5：已有输入不覆盖

预填只在输入框为空时发生（`setPrompt(current => current.trim() ? current : importPrompt(name))`）。用户正在写需求时导入文件，只会多出一个附件，不会吞掉已写的内容；需要提取指令时可以手动输入或清空后重新导入。

## Risks / Trade-offs

- **契约文件不再无损导入**：Agent 重新生成可能改变 hash。缓解：提示词要求沿用取值；需要严格往返时使用 CLI 或后续补精确入口。
- **导入本身不发请求**：确认前可以改指令、移除附件；代价是多一次点击，且用户可能忘了发送就离开页面（附件与草稿都只存在当前会话）。
- **大文件与不支持类型**：入口不再提前校验，由 `attachmentContext()` 在发送时拒绝（文本 100KB、单文件 12MB、最多 6 个），错误以失败轮次呈现，而不是入口 banner。
- **入口文案与实际能力的落差**：菜单仍叫「导入 DESIGN.md / CSS」，但不再解析 CSS 令牌。当前 CSS 也只作为参考文本，与 `attachmentContext` 的能力一致。

## Open Questions

- 是否需要保留一个显式的「精确导入契约 DESIGN.md」入口（例如菜单二级项），供往返验证与高级用户使用？当前不做，等实际需求出现。
- Agent 提取后是否要在对话里标注「其中 N 项来自 frontmatter」？当前只显示文件名的参考记录。
